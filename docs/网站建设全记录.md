> 这份文档写给**完全不懂技术**的人。目标只有一个：读完以后，你能明白这个网站是怎么回事，也能把它讲给别人听。

## 第一部分：先搞清楚，一个网站到底是什么

### 1.1 用一家餐厅来打比方

一个网站，和一家餐厅的结构几乎一模一样。

| 餐厅里的角色 | 网站里对应的东西 | 它能干什么 |
| --- | --- | --- |
| 店面和装修 | **网页（前端）** | 客人看到的样子：招牌、菜单、桌椅摆放 |
| 菜单和菜谱 | **HTML / CSS / JavaScript 文件** | 决定页面上有什么、长什么样、点了会怎样 |
| 服务员 | **后端接口（云函数）** | 客人点单，他去后厨下单，再把菜端出来 |
| 后厨和仓库 | **数据库** | 所有食材和配方真正存放的地方，客人进不去 |
| 门牌地址 | **域名** | 别人怎么找到你这家店 |
| 营业执照 | **备案**（国内才需要） | 用国内服务器 + 自己域名时需要的登记 |

关键点只有一句话：**客人（浏览器）永远不能直接进后厨（数据库）**，必须通过服务员（后端）传话。这一点是理解后面所有内容的地基。

### 1.2 五个角色，各管一段

打开这个网站的任意一个页面，背后只有五个角色在干活：

1. **浏览器**：你手机或电脑上的 Chrome / Edge / Safari。它负责显示画面、接收你的点击。
2. **网页文件**：三个文件就能组成一个网页 —— HTML 管结构、CSS 管样子、JavaScript 管行为。
3. **后端（云函数）**：一段跑在云端服务器上的程序。所有「读数据、写数据」的请求都要经过它。
4. **数据库**：一张张表格，存着配方、材料、账号、帖子、评论。
5. **网络**：把上面四样东西连起来的通道。

### 1.3 「前端」和「后端」到底在分什么

这两个词听起来很专业，其实分界线很朴素：

- **前端**：跑在**用户的设备**上。用户看得见、改得了。所以前端里的东西**都不能算秘密**。
- **后端**：跑在**服务器**上。用户看不见、碰不到。所以密码规则、权限判断这些必须放在后端。

举个例子：网页上有个按钮写着「删除帖子」。前端只是把这个点击变成一个请求发出去，**真正判断「你有没有资格删」的是后端**。如果把判断只写在前端，懂技术的人改一改页面就能删掉任何人的帖子。

这条原则在这个项目里从头到尾都在用，后面第四部分会讲它是怎么救了我们两次的。

## 第二部分：这个网站用了哪些技术

### 2.1 一张总表

| 部位 | 用了什么 | 为什么用它 |
| --- | --- | --- |
| 网页界面 | 原生 HTML + CSS + JavaScript | 不用框架，文件少、看得懂、打开就能改 |
| 网页放在哪 | 腾讯云静态托管 + GitHub Pages | 两个地址互为备份，国内国外都有人能打开 |
| 后端 | 腾讯云开发 CloudBase 的**云函数**（Node.js） | 不用自己买服务器、配环境，写一段代码就能跑 |
| 数据库 | **PostgreSQL**（腾讯云开发的 SQL 数据库） | 老牌关系型数据库，存表格数据最稳 |
| 登录凭证 | **token**（令牌） | 登录一次，之后不用反复输密码 |
| 密码存储 | **scrypt 加盐哈希** | 数据库里不存明文密码，泄露了也没法直接登录 |
| 注册验证码 | **SMTP 邮件**（QQ 邮箱） | 免费，个人就能做 |
| 内容审核 | 关键词规则 + 腾讯混元 AI（可选） | 先自动过滤明显的广告和辱骂 |
| 本地缓存 | 浏览器 **localStorage** | 打开更快，网络断了也能看到内容 |

### 2.2 HTML、CSS、JavaScript —— 网页三件套

这三个是**所有网站的共同基础**，不管大公司用什么工具，最后到浏览器里都是它们。

- **HTML**：页面的骨架。比如「这里有一个标题、一张图、一个按钮」。
- **CSS**：页面的样子。颜色、字号、间距、动画、手机上怎么排列。
- **JavaScript**：页面的行为。点一下会发生什么、数据怎么显示出来。

我们网站里对应这几个文件：

| 文件 | 行数 | 干什么的 |
| --- | --- | --- |
| `index.html` | 66 行 | 页面骨架，很短，主要放导航和几个空容器 |
| `assets/css/style.css` | 1202 行 | 全部样式（古典深色风格、手机适配、动效） |
| `assets/js/seed.js` | 2379 行 | **内容数据**：144 款配方、193 种材料、标签、拼音索引 |
| `assets/js/store.js` | 2219 行 | **数据层**：从哪读数据、往哪写数据 |
| `assets/js/app.js` | 2729 行 | **界面层**：每个页面怎么画、点了按钮做什么 |

把「数据」「数据层」「界面层」分成三个文件，是这套代码最重要的设计。好处是：

- 加配方只需要动 `seed.js`，不用碰界面代码；
- 以后换数据库（比如从本地换成云端），只动 `store.js`，界面**一行都不用改**。

实际上我们真的这么干了一次：从「数据存在浏览器里」换成「数据存在云数据库」，界面代码几乎没有改动。这就是分层的价值。

### 2.3 为什么没有用 Vue / React 这类框架

框架能帮大项目省事，但代价是：要装工具、要编译、出错时看不到具体原因。对一个初学者维护的小项目来说：

- 原生写法的文件打开就能读，改了刷新就见效；
- 不需要 `npm install`、不需要打包，服务器上也不用配置；
- 出问题时，报错行号直接对应你看得懂的代码。

代价是代码会更长一些（比如要手写「点击事件」的处理）。这个代价是值得的。

### 2.4 腾讯云开发 CloudBase —— 我们的后端和数据库

传统做法：买一台服务器 → 装系统 → 装数据库 → 配网络安全 → 部署程序。对个人很难。

腾讯云开发的思路是「开箱即用」，一个环境里就带了：

- **云函数**：写一段代码传上去，它就变成一个可以调用的接口；
- **SQL 数据库**：现成的 PostgreSQL，建表、查数据都在网页控制台里点；
- **静态托管**：把网页文件传上去就能访问；
- **HTTP 网关**：给云函数一个网址，让浏览器能访问到它。

我们用到的环境 ID 是 `cocktail-d1gk02vdl123a2e05`，地域是上海。

### 2.5 云函数是什么，为什么必须要有它

**云函数，就是一段「放在云上、别人通过一个网址来调用」的代码。**

它在我们这个网站里干的活：

```
浏览器  ──请求──►  云函数  ──读写──►  数据库
   ▲                  │
   └──────结果────────┘
```

为什么不能让浏览器直接连数据库？三个理由：

1. **数据库密码会暴露**：网页上的代码谁都能看，密码写在那里等于把钥匙贴在门上。
2. **权限没法控制**：谁都能删任何数据，包括删掉整个配方库。
3. **规则没法集中**：比如「只有作者能删自己的帖子」，这种判断必须由一个统一的、用户改不了的地方来做。

云函数还负责这些事：

- 登录时核对密码、发放 token；
- 判断你是不是管理员；
- 发注册验证码的邮件；
- 处理帖子审核；
- 出错时返回一句能看懂的中文提示。

我们这份云函数在 `cloud/api/index.js`，一共 1173 行，覆盖了 25 个左右的接口。

### 2.6 PostgreSQL —— 数据存在哪里

数据库里是一张张**表**，和 Excel 有点像，但更严格。我们一共建了 9 张表：

| 表名 | 存什么 |
| --- | --- |
| `users` | 账号（邮箱、昵称、加密后的密码、角色、收藏） |
| `sessions` | 登录状态（谁登录了、什么时候过期） |
| `recipes` | 配方（名字、材料、步骤、标签、配图） |
| `ingredients` | 材料库（名称、分类、别名、拼音） |
| `comments` | 配方评论 |
| `posts` | 交流区的帖子 |
| `reports` | 用户提交的勘误 |
| `settings` | 站点设置（站名、标语、各种开关） |
| `verify_codes` | 注册验证码（邮箱、验证码、有效期） |

举一个实际的例子，`recipes` 表里的一行大概长这样（简化）：

| id | name | glass | tags | items | steps |
| --- | --- | --- | --- | --- | --- |
| negroni | 尼格罗尼 | 古典杯 | `["苦","草本"]` | `[{"id":"gin","amount":"30 ml"}, …]` | `["材料加冰搅拌", …]` |

注意：**一条配方只用一行就存完了**，材料和步骤直接以 JSON 的形式塞在同一个格子里。好处是读取简单，不用为「材料清单」单独建一堆表。

### 2.7 localStorage —— 浏览器里的小仓库

除了云数据库，浏览器自己也能存一点数据，叫 `localStorage`。我们用它做两件事：

1. **缓存一份数据**：打开页面时先用本地这份立刻画出画面，不用干等网络；
2. **记住你的登录 token**：这样关掉页面再打开还是登录状态。

它的特点是：**只存在你这台设备上**，换电脑就没了，清了浏览器缓存也没了。所以它只能当缓存，不能当仓库。

### 2.8 验证码邮件是怎么发出去的（SMTP）

注册要验证邮箱，就得真的发一封邮件。发邮件用的是一个几十年的老协议，叫 **SMTP**。

流程是：

1. 用户点「获取验证码」；
2. 云函数随机生成一个 6 位数，存进 `verify_codes` 表，记下 10 分钟后过期；
3. 云函数通过 SMTP 连到 QQ 邮箱的服务器，把这封邮件交出去；
4. QQ 的服务器负责投递；
5. 用户填回来的验证码，云函数再和数据库里那条比对，对了就作废它（防止一个码用两次）。

要注意的是：连 SMTP 需要一个**授权码**（在 QQ 邮箱设置里生成），它不是 QQ 密码。授权码只存在云函数的环境变量里，不写在代码中，因为代码是公开的。

### 2.9 网页文件放在哪里

网页文件本身是「死」的，不需要计算，所以放在哪都行，只要浏览器能下载到。我们放了**两份**：

| 地址 | 特点 |
| --- | --- |
| 腾讯云静态托管 | 和数据库在同一个云、同一个城市，国内打开快 |
| GitHub Pages | 代码仓库自带的功能，国外访问更稳 |

两份指向同一份代码、同一个数据库，数据完全一样，互为备份。

### 2.10 域名、HTTPS、备案（了解一下就行）

- **域名**：就是 `xxx.com` 这种好记的地址。现在用的是云服务商给的免费地址，够用。
- **HTTPS**：网址前面那个小锁，表示传输过程加密。现在两个地址都是 HTTPS。
- **备案**：国内服务器绑自己的域名需要在工信部登记，免费但要等 2–3 周。不绑自己的域名就不需要。

## 第三部分：打开网页的那几秒，到底发生了什么

这部分把「原理」串成一条线。看懂了这段，你就真的懂网站了。

### 3.1 打开首页的完整流程

```
① 你在地址栏输入网址，按回车
   浏览器去问 DNS：这个地址对应的服务器在哪？

② 浏览器向那台服务器要 index.html
   拿到一个 66 行的骨架文件

③ 浏览器读这个文件，发现它引用了 CSS 和 3 个 JS 文件
   于是继续把这些文件下载下来

④ JavaScript 开始运行：
   先看本地缓存里有没有数据
   → 有，就立刻把页面画出来（这一步让你不觉得卡）

⑤ 同时向云函数发一个「把数据都给我」的请求（bootstrap）

⑥ 云函数收到请求：
   先看你是谁（有没有带登录 token）
   然后去数据库把配方、材料、帖子、评论、设置全部读出来

⑦ 数据回到浏览器，把画面用最新数据重画一遍

⑧ 你看到完整的首页，整个过程通常不到 1 秒
```

第 ④ 步和第 ⑦ 步是重点：**先用缓存画一遍，再用云端数据刷一遍**。这样网络慢的时候你也不会盯着白屏。反过来说，如果这两步的数据结构对不上，就会出现「明明有图却显示成 emoji」这种怪事 —— 第四部分会讲到。

### 3.2 登录时发生了什么

```
① 你填邮箱和密码，点登录
② 浏览器把这两样东西发给云函数（注意：密码只在这一步传一次）
③ 云函数从数据库里按邮箱找到你这个账号
④ 用你填的密码 + 数据库里存的"盐"，重新算一次哈希
⑤ 算出来的结果和数据库里存的哈希比对，一样就通过
⑥ 生成一串随机字符（token），存进 sessions 表，并返回给浏览器
⑦ 浏览器把 token 存在本地，之后每次请求都带上它
```

关键点：**密码从头到尾没有被存起来**，数据库里只有一个「算出来的指纹」。

### 3.3 注册时发生了什么

```
① 你填昵称、邮箱，点"获取验证码"
② 云函数生成 6 位数字，存进 verify_codes 表，并通过邮件发出去
③ 你把验证码和密码填好，点注册
④ 云函数核对验证码是否正确、是否过期
⑤ 正确 → 把验证码删掉（一个码只能用一次）
⑥ 用 scrypt 给密码加盐算出哈希
⑦ 往 users 表插入一行新账号
⑧ 顺手帮你登录（发一个 token）
```

### 3.4 发帖时发生了什么

```
① 你写好标题、正文、图片，点发布
② 云函数先检查：有没有登录？内容长度是否合理？
③ 跑一遍关键词规则（广告词、手机号、外链、辱骂等）
④ 风险分很低 → 直接发布；风险中等 → 标记"待审核"转人工；风险很高 → 直接拒绝
⑤ 插入 posts 表，返回给浏览器
```

这一套叫「三层审核」：规则 → AI → 人工。它的好处是绝大部分正常内容不用人工过，站长只需要处理少数可疑的。

### 3.5 为什么要有 token

HTTP 协议本身是「无记忆」的：它不知道这一次请求和上一次是不是同一个人。所以需要一个凭证，就是 token。

打个比方：token 就是游乐园的手环。进门时验一次身份、发一个手环，之后玩每个项目只认手环，不用每次出示身份证。

我们的 token 存在 `sessions` 表里，30 天过期。退出登录 = 丢掉手环。

## 第四部分：几个必须懂的原理（都是踩坑换来的）

这一部分是全篇最「值钱」的，因为每一条都对应一次真实的故障。

### 4.1 密码为什么不能存明文

如果数据库里存的是 `123456`，那么任何一个能看到数据库的人（包括误操作的自己、被黑的服务器）就拿到了所有人的密码 —— 而且很多人会在别的网站用同一个密码。

正确做法是存「哈希」：

```
密码 + 随机盐  →  一串固定的计算  →  一串看不出规律的字符
```

- **哈希**：单向计算，算得出来、反不回去。
- **盐**：每个账号一个随机字符串，加进去，让「同一个密码」在两个账号里算出的结果也不同，防止有人拿现成的密码表去撞。

我们用的是 Node.js 自带的 `scrypt` 算法，算出来的哈希是 128 位十六进制字符。**即使数据库被人拿走，也没法直接登录。**

### 4.2 跨域（CORS）—— 那个「新域名连不上云端」

这是上线过程中最典型的一个坑。

**什么是跨域**：浏览器有一条安全规则 —— 如果网页来自 A 域名，要访问 B 域名的接口，B 必须明确说「我允许 A 来访问」。这句话写在响应头里，叫 `Access-Control-Allow-Origin`。

我们的情况：网页在 `...tcloudbaseapp.com`，接口在 `...ap-shanghai.app.tcloudbase.com`，属于跨域，需要许可。

**故障现场**：用 GitHub 的地址访问一切正常，换成腾讯云的新地址就报「云端连接失败」。

**原因**：腾讯云的网关遇到「本环境自己的域名」时，会自动补一句「我允许这个来源」，而我们的云函数又写了一句「我允许所有来源（`*`）」。两句话被合并成一句 `你的域名,*` —— 这在浏览器眼里是**非法值**，只认「一个精确域名」或「星号」，于是整个请求被拒。

**解决**：让云函数在遇到自家域名时**不要说这句话**，交给网关去说；其它来源（比如 GitHub）还是由云函数说 `*`。

**教训**：同一件事只能有一个地方负责。两个地方都抢着说，结果就是互相打架。

### 4.3 缓存 —— 为什么改了代码手机还是旧版

浏览器为了省流量，会把 CSS、JS 这些文件存在本地。如果你改了 `app.js`，浏览器可能还在用昨天那份。

解决办法是给文件加一个「版本号」：

```html
<script src="assets/js/app.js?v=20"></script>
```

只要 `v=` 后面的数字变了，浏览器就认为这是一个新文件，重新下载。**这个数字从 v1 一路涨到了 v20**，每次改动都会加一。

另外，页面底部一直显示着版本号，这是故意的：你随时能确认自己看到的是不是最新版。

### 4.4 数据「归一化」—— 为什么图片闪一下变回 emoji

这是最后一个被发现的 bug，也最能说明「分层」的价值。

**故障现象**：配方库里所有酒都只显示 emoji；刷新页面时，图片会闪一下，然后又变回 emoji。

**排查思路**：

1. 图片地址存在吗？—— 存在，数据库里有 63 张图。
2. 那为什么看不到？—— 去看界面代码用的是哪个字段。
3. 界面卡片用的是 `imageThumb`（缩略图字段），而不是 `image`。

**原因**：数据从云端回来以后，少跑了一道「整理」工序（代码里叫 `normalizeRecipe`），而这道工序负责补上缩略图字段。于是云端来的每款酒都没有缩略图，界面只好显示 emoji。

至于「闪一下」：页面先用**本地缓存**画了一遍（本地这份跑过整理工序，有缩略图），随后**云端数据**覆盖上来（没有缩略图），所以图就消失了。整个现象在一秒内发生，看起来就像"闪了一下"。

**解决**：让云端数据也走一遍整理工序；顺便把「图片地址为空就回退到默认图」这条规则补上。

**教训**：数据从不同地方来的时候，都要走同一道加工流程，不能有的加工、有的不加工。

### 4.5 缩略图与分辨率 —— 首页大图为什么糊

同一个图片源，存在两种尺寸：

- 列表卡片用小图（省流量、加载快）；
- 首页大图用原图（清晰）。

一开始首页也用了小图，被放大以后就糊了。后来改成：**卡片用缩略图，大图用原图，但把显示尺寸缩小**。这样既清晰，又不会让图片撑爆版面。

### 4.6 为什么后来要把管理端也接上云

有一段时间，管理员在后台改材料、改配方图片，界面上看着改了，**一刷新就打回原形**。

原因：这些操作当时只改了浏览器里的数据，没有发给云函数，所以数据库里根本没变，下次拉数据自然又被覆盖回去。

这件事说明：**只要涉及"要留下来的改动"，就必须写到数据库**。界面上显示成功不代表真的成功了。

### 4.7 免费版没有自动备份怎么办

云数据库的自动备份要付费版才有。免费版的对策是：

**在管理后台加一个「下载完整备份」按钮**。点一下，把数据库里所有表导出成一个 JSON 文件下载到本地。建议每一两周点一次，存到网盘。

这就够了：出问题时至少有完整的一份数据在手。**备份的关键不是自动化，而是"确实有一份在别处"。**

## 第五部分：这个网站是怎么一步步长出来的

整个过程有 36 次提交（每次提交 = 一次改动存档）。按时间顺序分成五个阶段。

### 阶段一：先做一个能看的原型（第 1–3 次改动）

最初的名字叫「今晚喝什么」，目标只是「一个能看配方、能按材料找酒的网页」。

这时候所有数据都存在浏览器里 —— 你和朋友打开同一个网址，看到的是**两份互不相干的数据**。

> 这一步的价值：先确认「这个东西值得做」，再投入精力搞后端。做原型永远比做成品便宜。

### 阶段二：内容和体验（第 4–20 次改动）

这一步主要是在「用起来像不像样」上下功夫：

| 做了什么 | 为什么 |
| --- | --- |
| 加了管理员权限体系 | 有人管才能开放给用户 |
| 加了评论区 | 让配方能被讨论、被纠正 |
| 配方和材料大幅扩充 | 内容量是这类网站的根本 |
| 站点更名为「鸡尾酒法典」 | 原来的名字太像小程序，不够正式 |
| 给配方配图 | 有图的列表比纯文字好看太多 |
| 加口味标签 + 「想喝啥」页面 | 用户不一定会用搜索，但一定会点标签 |
| 手机端导航收成抽屉菜单 | 顶部把七个入口挤成一坨，手机上没法看 |
| 整体风格古典化、减少 emoji | 用字体大小和间距来区分层级，比贴 emoji 高级 |
| 材料按分类 + 拼音排序、加 A–Z 索引 | 190 多种材料，没有索引根本翻不动 |
| 加勘误系统 | 配方总会有错，得让用户能报错 |
| 加每日推荐主页 | 首页要有"逛"的感觉，不能直接甩一个列表 |
| 发帖 + 三层审核 | 让用户能交流，同时挡住广告 |
| 改成手机端也能看清的排版 | 大部分访问来自手机 |

### 阶段三：上云（第 21–27 次改动）

这一步是质变：数据从「各人自己的浏览器」搬到「一个共同的地方」。

具体做了：

1. 写建表脚本，在云数据库里建 9 张表；
2. 把 144 款配方、193 种材料写成 SQL 一次性导进去；
3. 写云函数，提供登录、注册、发帖、评论等接口；
4. 把前端的数据层改成「先读缓存、再拉云端」；
5. 修了一堆只有真上云才会遇到的报错（schema 名字不对、权限不足、字段缺失等）。

这一阶段最大的收获是：**前端分层设计救了命** —— 换数据来源只改了 `store.js`，界面代码基本没动。

### 阶段四：账号体系（第 28–30 次改动）

期间尝试过手机号注册（配合短信验证码），后来发现腾讯云短信的签名资质不对个人开放，还要求运营商实名报备 7–10 个工作日。

于是改成**邮箱验证码**：用 QQ 邮箱的 SMTP 免费发送，个人立刻就能做通。

这一步踩的坑值得记一下：

- **第一个邮箱账号能注册，第二个就报错**。原因是建表时写了一句「手机号不能重复」，而邮箱注册时手机号是空的 —— 第一个人把"空手机号"占住了，第二个人就撞上了。修法是把约束改成「只有真的填了手机号才要求唯一」。

> 这类 bug 只有真人来用才会暴露，所以上线前一定要拉朋友试一遍。

### 阶段五：上线与收尾（第 31–36 次改动）

| 做了什么 | 说明 |
| --- | --- |
| 管理端功能上云 | 后台改材料、改图、管用户、处理勘误，都能真正存下来了 |
| 加一键完整备份 | 替代免费版没有的自动备份 |
| 网页搬到腾讯云静态托管 | 国内访问速度大幅提升 |
| 修跨域头非法的 bug | 见 4.2，只有换域名才会暴露 |
| 每日推荐改成两侧悬浮箭头 | 电脑上用鼠标拖动很不顺手 |
| 修 emoji 那个 bug + 扩充 29 款经典 | 见 4.4 |

### 附：内容规模的变化

| | 最初 | 现在 |
| --- | --- | --- |
| 配方 | 十几款 | **144 款**（135 经典 + 9 特调） |
| 材料 | 几十种 | **193 种** |
| 配方配图 | 0 张 | **110 张** |
| 数据库表 | 0 | 9 张 |
| 云函数接口 | 0 | 约 25 个 |

## 第六部分：网站现在的样子

### 6.1 文件结构

```
index.html                    页面骨架（66 行）
assets/
  css/style.css               全部样式（1202 行）
  js/seed.js                  内容数据：配方、材料、标签（2379 行）

  api/index.js                云函数：所有后端接口（1173 行）

  review-post/                AI 审核云函数（可选部署）
docs/                         各种说明文档
serve.js                      本地预览用的小服务器（52 行）
```

### 6.2 三种身份，各自能做什么

| 能做的事 | 游客 | 注册用户 | 管理员 |
| --- | :---: | :---: | :---: |
| 浏览配方、材料、帖子、评论 | 可以 | 可以 | 可以 |
| 收藏、勾选自己的材料 | — | 可以 | 可以 |
| 发帖、评论、点赞 | — | 可以 | 可以 |
| 发布配方、补充视频 | — | 可以 | 可以 |
| 提交勘误 | — | 可以 | 可以 |
| 材料增删改、配方审核、评论管理 | — | — | 可以 |
| 用户管理、站点设置、数据备份 | — | — | 可以 |

关键是：**这些权限判断全部写在云函数里**，不在网页上。网页上就算看到了按钮，没权限也调不动。

### 6.3 页面上有什么

- **首页**：每日推荐（4 杯大图卡片，左右切换）+ 交流区最新帖子 + 快捷入口 + 酒库统计
- **配方库**：144 款，支持搜索、筛选、排序、收藏
- **想喝啥**：28 个口味标签分组，点标签筛酒 + 随机抽一杯
- **我有啥**：勾材料 → 分三档推荐 + 补货建议
- **添加配方**：昵称、材料、步骤、图片、标签、可选视频
- **交流区**：发帖、回帖、点赞、收藏、按热度/时间排序
- **我的**：身份权限、收藏、自己发的配方、我的材料、改密码
- **管理后台**：材料管理、配方管理、帖子审核、评论管理、勘误处理、用户管理、站点设置、数据备份

## 第九部分：怎么把这些讲给别人听（5 分钟版）

如果别人问「你这个网站是怎么做的」，可以按这五步说：

**第一分钟：是什么、解决什么问题**

「我做了个调酒配方网站，解决三个问题：不知道调什么、买了酒用不完、配方不敢改。它有个配方库，还能按你手头有的材料找酒。」

**第二分钟：一个网站由什么组成**

「一个网站就三部分：前面是网页，管展示；中间是后端，管处理请求；后面是数据库，管存东西。浏览器不能直接连数据库，一定要经过后端，不然密码和权限就没法保护。」

**第三分钟：用了什么技术**

「界面是用最基础的 HTML、CSS、JavaScript 写的，没用框架，图的是文件少、改起来直观。后端用的是腾讯云开发的云函数，数据库是 PostgreSQL，登录用邮箱加验证码，网页托管在腾讯云和 GitHub 上，两个地址互为备份。」

**第四分钟：几个有意思的坑**

「遇到过几个典型问题：一个是换域名以后接口全连不上，原因是跨域许可被写了两遍，浏览器认成非法值；一个是配方图片全变成了 emoji，因为云端数据少走了一道加工流程。这两个都不是功能写错，而是对规则理解不够。」

**第五分钟：现在和下一步**

「现在上面有 144 款配方、193 种材料，110 张配图，账号、发帖、评论、审核、备份都能用。下一步想补的是把剩下没图的配方配上图，以及加一个用户协议和隐私政策。」

## 最后

做这个网站用到的技术都不算新，但组合起来能解决一个真实的小问题。真正花时间的部分不是写代码，而是：

- 把需求想清楚（哪些功能先做，哪些不做）；
- 把数据分好层（内容和界面分开）；
- 把每个报错查到根因（而不是绕过它）。

如果你也在做类似的东西，这三条比任何技术选型都重要。
